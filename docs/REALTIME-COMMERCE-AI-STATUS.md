## Production architecture

1. **Static frontend:** renders catalogue, cart, checkout and order status. It never stores provider secrets or AI API keys.
2. **API gateway/backend:** authenticates the user, validates SKU and price against the server catalogue, calculates totals, creates transaction IDs, and enforces state transitions.
3. **Database:** persists users, products, orders, payment attempts, webhook events, expiry timestamps and audit logs. Use migrations and least-privilege access.
4. **Payment provider:** create a QRIS payment session server-side. Store provider reference and expiry. Mark an order paid only after validating the provider's signed webhook or a server-to-server status check. Never trust a browser redirect or screenshot as payment proof.
5. **Expiry/reconciliation worker:** expires unpaid orders using server time and checks uncertain payment states with the provider before finalizing them.
6. **WhatsApp Business:** send order/payment updates from the backend after state changes. Treat delivery as asynchronous; do not claim a message was delivered without provider confirmation.
7. **AI endpoint:** calls the selected model from the server. Give it only necessary order context, redact sensitive data, require authorization before looking up an order, and never let model output directly mark an order paid or issue a refund.
8. **Live updates:** push server-confirmed order changes through SSE/WebSocket where available; retain polling as a fallback. Display the last successful sync time and a stale/offline warning.

## Environment variables (server only)

Configure these in the hosting provider's secret manager, never in Git or static frontend files:

- `DATABASE_URL` or managed database connection settings
- `SUPABASE_URL` and server-side key only if a trusted backend needs it
- `PAYMENT_PROVIDER_BASE_URL`, `PAYMENT_PROVIDER_API_KEY`, `PAYMENT_WEBHOOK_SECRET`
- `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_VERIFY_TOKEN`
- `AI_API_KEY`, `AI_MODEL`
- `APP_BASE_URL`

Use publishable browser keys only where designed for public use. Never use a service-role key, payment secret, WhatsApp token, or AI key in browser JavaScript or Git commits.

## Order state machine

Allowed state transitions must be enforced by the backend:

- `pending_payment -> paid` only after verified provider confirmation
- `pending_payment -> expired` only after server expiry and reconciliation
- `pending_payment -> cancelled` only after an authorized cancellation
- `paid -> fulfilled` only after fulfillment confirmation
- `paid -> refund_pending -> refunded` only through an authorized refund workflow

Duplicate webhook delivery must be idempotent. Store provider event IDs and reject invalid signatures. If payment status is ambiguous, show `verification_pending` rather than guessing.

“100% accurate” and “real-time” cannot be honestly guaranteed for every external service. The product should expose source, timestamp, sync health and uncertainty, and should never invent a live status. The current demo is not production-ready until the checklist above is completed and verified.
